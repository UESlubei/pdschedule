# 性能归因笔记（最终结论须用完整数据确认）

以下是已落盘轨迹支持的初步解释及后续核对项，不是五种子最终结论。

1. 首种子Joint在interference/transition实际Prefill步骤中约90%/98%处于最小256配额。相对纯Decode的1.2倍目标，在Mixed Step中未必可达；控制器压到下限仍不能保证目标。标定是服务端8步窗口的请求维度P90，评价是客户端P99，两者不能混同。
2. 首种子Joint interference的排队P95约13.9秒，Prefill开始到首输出的服务P95约0.89秒；最终TTFT约15秒。主要问题是小配额把等待队列放大，不只是一条Prompt被多切几次。
3. 小配额把6144输入拆为更多前向Step。每Step短了，但每Prompt重复固定前向成本更多。只有Nsight/实际Step数据才能支持具体GPU解释，不应仅凭Utilization宣称Tensor Core效率或带宽改善。
4. Load在高Decode期间往往等同固定512，所以需对照Fixed512；对“均衡目标”则用独立验证选出的Fixed2048。不能只和大预算原生对比。
5. 正式mixed使用共同2.422RPS，固定Trace吞吐接近约600tok/s是输入速率限制下的完成速率，不能声称最大吞吐或容量提高。
6. Decode数量内生于Prefill调度。更小Cap会让后续请求更晚进入Decode；必须同时看TTFT、实际Decode轨迹、完整请求成功率与吞吐，避免把延后入场当作免费ITL收益。interference主指标只比较已开始的初始Decode cohort，同Trace无丢弃。
7. Aging只提高总配额，不能直接释放序列槽。Running Prefill的无进度年龄每次推进即清零，不等于端到端TTFT年龄。因此即使没有永久饥饿，TTFT也可能较差。通过救援次数/实际带Prefill计算的救援次数与队列/槽位轨迹核对。
8. 控制窗口取各请求最近一次间隔，可能覆盖窗口早期瞬态尖峰；EWMA又有滞后。需要从K/alpha消融与原始间隔曲线确认，不能在未测前宣称某个参数更优。
9. 原生long threshold是单请求上限，多个Partial Prefill可能仍将总Step填满；项目是聚合配额。原生阈值对照未跑完前，不预设它必然劣于本方案。
10. 少量mixed步骤超过延迟表最高context档6400（长请求6144+512最高6656），已记录target_extrapolated_steps；该段用最近高成本档代理。性能数据仍真实，但不能声称目标标定覆盖所有上下文。
11. 连续压力输入有限且最后排空；若压力阶段队列增长，必须称为过载/持续高压有限流，不作稳态有界TTFT宣称。
12. 首轮正式种子后才开始连续硬件采样；未锁频，报告温度/功率/时钟范围及这一覆盖限制。核心在线实现/Trace生成/标定12项来源始终冻结，分析脚本变化另行记录。

正式5种子已完成（165Trial）：interference stock/load/joint/aging P99约252.54/64.02/47.56/89.20ms；PF95约9568.50/12153.72/15138.78/13629.82ms；输出595.84/534.35/489.29/506.45tok/s。Load vs stock配对P99变化-74.65% CI[-74.78,-74.53]，PF95+27.02%，吞吐-10.32%。原均衡约束未达成，不能只报-74.65%。相对验证所选F2048，Load仍以PF95+25.04%和吞吐-8.81%换取P99-60.37%。

持续压力首种子17：308请求全部完成；F512/Joint/Aging测量墙钟363.54/371.97/364.48秒，PF95约154.59/163.35/155.21秒，最大等待144/152/146。高Decode步占比约94.6%/95.1%/94.6%。Aging 2140个救援Step中仅320个有实际Prefill计算，说明多数救援受序列槽等原生条件阻塞；不能把raise cap视为有效进度。最大Chunk进度间隔61.58/63.11/99.03ms，与等待首个Chunk的上百秒必须分开。
